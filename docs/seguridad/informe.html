Resumen

Se auditaron la app Flutter y su API. De los diez riesgos del Top 10, 3 se cumplen y 7 tenían algo por corregir. Se registraron 8 hallazgos: 7 se corrigieron, cada uno en su propio commit con su ID, y se verificaron repitiendo la misma prueba. El hallazgo que queda abierto es de severidad baja y tiene un plan.

Los dos hallazgos más graves estaban en el servidor. Uno era una clave de firma de sesiones publicada en el repositorio (H-01): con ella cualquiera entraba como cualquier usuario. El otro, sesiones que no se podían cerrar (H-02): un token robado seguía sirviendo 90 días después de cerrar sesión.

Fase 1 · Modelo de amenazas

Diagrama de la app y flujo de datos

Regla base del data sheet: el teléfono y la app instalada no son de confianza. Por eso cada decisión (quién ve un chat, quién marca un acuerdo como entregado, quién descarga una foto) se valida en el servidor.

Fase 2 · Auditoría con OWASP Mobile Top 10 (2024)

Técnicas usadas (se pedían al menos dos; se usaron cinco)

TécnicaCómo se hizo
1. Búsqueda de secretos en el código y en el historial de GitScript propio (herramientas/secret-scan.py) que revisa cada línea agregada en los 33 commits de todas las ramas con patrones de claves (AWS, GitHub, Google, Resend, JWT, URL con contraseña, asignaciones de secretos). Se reemplazó a gitleaks porque no se usó Docker.
2. Análisis del APK de lanzamientoflutter build apk --release y luego aapt2 dump xmltree (manifest), apksigner verify --print-certs (firma), búsqueda de nombres dentro de libapp.so (ofuscación) y mapping.txt (R8).
3. Revisión de dependenciasnpm audit --omit=dev en el servidor y flutter pub outdated en la app.
4. Revisión de AndroidManifest.xml y permisosPermisos pedidos, componentes exportados, copias de seguridad, tráfico en claro.
5. Pruebas dinámicas contra la API localScript (herramientas/security-check.mjs) que intenta cada ataque contra el servidor con PostgreSQL local y dice si sigue abierto; más las 150 pruebas existentes de la API.

No se usó Logcat ni mitmproxy porque el equipo no tiene emulador Android ni teléfono conectado. La versión de depuración ya queda preparada para mitmproxy (H-06 acepta certificados del usuario solo en depuración).

Revisión de los diez riesgos

IDRiesgoEstadoJustificación
M1Improper Credential UsageNo cumpleLa clave JWT de respaldo estaba escrita en el código y publicada; start-local.cmd traía claves (H-01). No hay llaves de servicios de terceros en el código ni en el historial.
M2Inadequate Supply Chain SecurityNo cumple (parcial)Servidor: npm audit = 0 vulnerabilidades. App: 12 dependencias transitivas desactualizadas (H-07).
M3Insecure Authentication/AuthorizationNo cumpleEl servidor valida sesión y permisos en cada petición, pero cerrar sesión no invalidaba el token y este duraba 90 días (H-02).
M4Insufficient Input/Output ValidationCumpleEl servidor valida tipo y rango de cada campo (inRange, reglas CHECK), revisa el tipo real de las fotos y que cada foto sea del usuario. La app valida correo y contraseña. No hay deep links ni WebView.
M5Insecure CommunicationNo cumple (parcial)La API usa HTTPS y Android 9+ bloquea http por defecto, pero no había configuración explícita y la app aceptaba un servidor http en la versión publicada (H-06).
M6Inadequate Privacy ControlsNo cumple (parcial)Hay política de privacidad, eliminación de cuenta y permisos justificados (micrófono para dictado). Pero la app escribía el correo del usuario en los registros (H-05).
M7Insufficient Binary ProtectionsNo cumpleR8 activo para Java/Kotlin, pero el código Dart no estaba ofuscado: nombres como SessionLocalDataSource o saveToken se leían en el binario (H-03).
M8Security MisconfigurationNo cumpleSin modo debug en release, copias de seguridad apagadas y solo la actividad principal exportada. Pero el APK público iba firmado con la clave de depuración (H-04).
M9Insecure Data StorageCumpleEl token va en Android Keystore con flutter_secure_storage 11 (no usa la librería obsoleta EncryptedSharedPreferences); allowBackup=false. Queda una mejora baja: proteger la pantalla de capturas (H-08).
M10Insufficient CryptographyCumplebcrypt para contraseñas y códigos, HMAC-SHA256 para firmar fotos, JWT solo HS256, números aleatorios con crypto. No se usa MD5 ni SHA-1.

Recomendaciones y mejoras pendientes

#RecomendaciónPor qué
1Cerrar H-08: FLAG_SECURE en chat, cotización y contraseñaEvita que los precios y la negociación queden en capturas o en la vista de apps recientes. Hay que verificarlo en un teléfono.
2Cargar los secretos de firma en GitHub y crear la clave de lanzamientoDesde H-04, un Release sin ellos ya no se publica.
3Certificate pinning con plan de rotación (mejora opcional)Protege contra certificados emitidos a terceros; requiere un plan para cuando Railway renueve el certificado.
4Play Integrity en las acciones críticas (mejora opcional)Detecta APK modificados como el de la amenaza A3.
